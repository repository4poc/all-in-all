## Securly Connecting to RSD instance

1. Validate (From Local)- Check DNS using what type of IP and nslookup

```
nslookup <domain name>

nslookup type=ns <domain name>
```

- Here the IP is public (52.0.63.176) and no name server
  ![alt text](images/{2D16D593-68A6-404E-AE86-EBEECC7DA4CB}.png)

2. Validate (From EC2)

```
nslookup <domain name>

nslookup type=ns <domain name>
```

- Here the DNS is using the private IP, as we provided the access via security group from EC2 to RDS. So connection is through named server.
  ![alt text](images/{EB581E2A-11F6-48B8-964F-B2D0DD962BDC}.png)

```
Application on EC2
        |
        | Connect to:
        | mydb.abc123.us-east-1.rds.amazonaws.com
        |
        ▼
Amazon DNS Resolver
(inside the VPC)
        |
        | Resolves hostname
        ▼
10.0.2.145   (Private IP of the RDS instance)
        |
        ▼
RDS Database
```

**Step-by-step**

- Your application uses the RDS endpoint, for example:
  mydb.abc123.us-east-1.rds.amazonaws.com
- The EC2 instance sends a DNS query to the Amazon DNS Resolver provided in the VPC.
  - This is available automatically in every VPC.
  - By default, the resolver is at the VPC base address + 2 (for example, in 10.0.0.0/16, it's 10.0.0.2).
- The Amazon DNS Resolver returns the private IP of the RDS instance.

| Feature                      | Azure                                       | AWS                                                               |
| ---------------------------- | ------------------------------------------- | ----------------------------------------------------------------- |
| Application connects to      | Service FQDN                                | RDS endpoint                                                      |
| DNS inside private network   | Resolves to private IP via Private DNS Zone | Resolves to private IP via Amazon DNS Resolver                    |
| Separate internal hostname   | `*.privatelink.*`                           | Not typically exposed; the RDS endpoint itself resolves privately |
| Application changes required | No                                          | No                                                                |

**Azure**

| Client location                 | DNS resolves to | Connection path  |
| ------------------------------- | --------------- | ---------------- |
| Inside VNet with Private DNS    | Private IP      | Private Endpoint |
| Outside VNet                    | Public IP       | Public endpoint  |
| Inside VNet without Private DNS | Public IP       | Public endpoint  |

Technically, yes, but applications normally use only one.

- Public endpoint name: `myserver.database.windows.net` (the hostname your application connects to)
- Private Link hostname: `myserver.privatelink.database.windows.net` (used internally by Azure DNS)

In your VM/app, you normally do not explicitly call the Private Link hostname.

You keep using the normal service FQDN:

```
myserver.database.windows.net
        ↓ CNAME
myserver.privatelink.database.windows.net
        ↓ A record in Private DNS Zone
10.x.x.x private endpoint IP
```

- Azure is not security-group-to-security-group like AWS.
- In Azure, think in subnets + Private Endpoint / VNet rules, not “add VM/App Service security group to SQL.”

For Azure VM → Azure SQL:

- Put the VM in a VNet/subnet.
- Create a Private Endpoint for Azure SQL in that VNet.
- Configure Private DNS so yourserver.database.windows.net resolves to the private IP.
- Optionally disable Public network access on Azure SQL.

Azure Private Endpoint gives Azure SQL a private IP inside your VNet. That is the closest equivalent to “private RDS access.”

For Azure App Service → Azure SQL:

- Enable VNet Integration on the App Service.
- Create an Azure SQL Private Endpoint in the same VNet, or a peered/reachable VNet.
- Configure Private DNS.
- Disable public access on SQL if you want private-only access.

App Service VNet Integration lets the app make outbound calls into a VNet; the SQL Private Endpoint provides the private target

| AWS                              | Azure                                                   |
| -------------------------------- | ------------------------------------------------------- |
| RDS security group allows EC2 SG | Azure SQL firewall/VNet rule allows subnet              |
| Private RDS endpoint in VPC      | Azure SQL Private Endpoint in VNet                      |
| EC2 in private subnet            | Azure VM in VNet subnet                                 |
| Elastic Beanstalk app instances  | App Service with VNet Integration                       |
| Security group reference         | Usually subnet-based access, Private Endpoint, NSG, DNS |

## SQL vs NoSQL

- SQL/Relational Databases
  - Fixed Schema
  - Store data in Tables
  - Have relationships between Tables
  - Transactional (ACID - Atomicity, Consistency, Isolatio, Durability)
    - Atomic set of actions : either all actions or none
  - Support SQL for Query
  - Due to Fixed schema, not to much performance and scalable
- Databases who support ACID charactristics, is categorized as Transactional

- NoSQL Databases
  - Emphasise on Performance and Scale
  - No Fixed Schema / Schemaless
  - I can have billions of entities
  - Data Usually stored in JSON format
  - Transactions: Use concept of Consistency
    - Eventual Consistency
  - Data Can be temporary inconsistent
  - No SQL Database only support part of ACID
  - No standard query language, each No SQL database has its own query language.
  - MongoDB (OpenSource) / CosmosDB (Azure) / DynamoDB (AWS)
  - MongoDB recently added Transaction Support

## Indexes

| Feature                 | DynamoDB                           | Cosmos DB                         |
| ----------------------- | ---------------------------------- | --------------------------------- |
| Default indexing        | Primary key only                   | All properties indexed by default |
| Secondary indexes       | GSI, LSI                           | Automatic indexes on properties   |

| Customize indexing      | Create GSIs/LSIs                   | Modify indexing policy            |

| Separate throughput         | Yes (or shares on on-demand)               | Shares table throughput                       |
| Storage                     | Separate copy of indexed attributes        | Shares table partitions but stores index data |

## DynamoDB Streams

- Equivalent to CosmosDB change feed
- Stream of Events capture data modification in the database
  - item added
  - item updated
  - item deleted

| Feature             | DynamoDB Streams                 | Cosmos DB Change Feed                                                                        |
| ------------------- | -------------------------------- | -------------------------------------------------------------------------------------------- |
| Purpose             | Capture item changes             | Capture item changes                                                                         |
| Events              | Insert, Update, Delete           | Insert, Update (deletes require full-fidelity mode)                                          |
| Ordering            | Ordered within a partition/shard | Ordered within a logical partition                                                           |
| Retention           | 24 hours                         | Continuous (latest version mode); effectively persists while data exists, with checkpointing |
| Consumer            | Reads from stream shards         | Reads from the change feed                                                                   |
| Typical integration | AWS Lambda, Amazon Kinesis       | Azure Functions, SDK Change Feed Processor                                                   |

## DynamoDB Query Language
